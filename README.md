# Billing Reports

A billing application with authentication and a charges report, designed for
tables in the millions of rows.

[![CI](https://github.com/Santiann/billing-reports/actions/workflows/ci.yml/badge.svg)](https://github.com/Santiann/billing-reports/actions/workflows/ci.yml)

| | |
|---|---|
| **Backend** | PHP 8.3 + Laravel 13 (REST API) |
| **Frontend** | Next.js 16 (App Router) + TypeScript |
| **Database** | MySQL 8 |
| **Infrastructure** | Docker + Docker Compose |

Every number quoted here was **measured** against a base of 2,000,000 billings
and 5,000 customers, generated by the project's seeder. Each measurement is
recorded with its `EXPLAIN` alongside in
[docs/performance.md](docs/performance.md) — and what was discarded is there too,
with the number that justified discarding it.

**The code is in English and the interface is in Portuguese, on purpose.**
Identifiers, comments and documentation are English because that is who reads
them. Everything a user reads stays in pt-BR because the product is for the
Brazilian market, and that is what decides the rest: CPF and CNPJ as the
customer's identity, the CSV written with a semicolon and a comma decimal so it
opens correctly in Excel in Portuguese, validation messages field by field, and
the routes the user sees in the address bar. None of that is a translation
someone forgot.

## Running it

The only prerequisite is Docker with Compose v2.

```bash
git clone https://github.com/Santiann/billing-reports.git
cd billing-reports
make install
```

Without `make`: `docker compose up -d` and, once the migrations have run,
`docker compose exec php php artisan db:seed`.

| | |
|---|---|
| Application | http://localhost:3000 |
| API and documentation | http://localhost:8000 |
| Administrator | `admin@billing.test` / `password` |
| Read-only role | `consulta@billing.test` / `password` |

There is no `.env` to copy and no `composer install` to run: the entrypoint
installs the dependencies, creates the `.env`, generates the `APP_KEY` and runs
the migrations.

To generate measurement volume: `make seed-volume`. How long a clean install
takes, phase by phase, is in
[docs/operations.md](docs/operations.md#how-long-a-clean-start-takes), along with
the eleven Makefile targets and what each one does.

## Testing it

```bash
make test     # 283 tests, 1,070 assertions · 97.44% of lines covered
make e2e      # 10 end-to-end tests (Playwright), against the running stack
make lint     # Pint on the backend; typegen, typecheck and ESLint on the frontend
```

The suite runs on **MySQL**, not SQLite, and the reason is the rule below: on
SQLite the consistency test would be validating a different engine — `POW()`
does not even exist by default. CI runs the suite and the lint on every push;
the end-to-end tests stay outside it because they would require bringing the
whole stack up on the runner.

Details, coverage and the traps the suite had to solve:
[docs/testing.md](docs/testing.md).

## The rule that governs the architecture

**The updated value of an overdue billing has to be computable in SQL.**

The report sorts by updated value and sums the interest of the **entire**
filtered set. If the calculation existed only in PHP, either of those two
operations would force loading the whole result into memory — which the brief
explicitly rules out.

Almost everything else in the project follows from that:

- `InterestCalculator` is the **single source** of the rule and has two faces:
  one that generates SQL, used in the listing and in the aggregations, and one in
  PHP, used to display a single billing. **A test asserts the two agree down to
  the cent** — and it is the most important test in the repository.
- Compound interest: `original_amount * (1 + monthly_rate) ^ (days_late / 30)`.
- The reference date **comes down from PHP**, never `CURDATE()`. That is what
  makes the calculation testable with frozen time, and what makes it possible to
  compute interest at the payment date.
- A paid billing **accrues no interest**: it freezes at the moment of payment,
  and the displayed value comes from the stored columns.
- "Overdue" is not a stored status: it is `pending` with the due date in the
  past, and the same condition exists on both faces.

The full design — modelling, authentication, Next's two API origins, service
naming — is in [docs/architecture.md](docs/architecture.md).

**Required:** token authentication, customer and billing records, compound
interest on arrears, a report by period with filters, sorting and totals all
resolved in the database, CSV and PDF exports, indexes, one-command Docker and an
automated suite.

**Beyond that**, each with its decision recorded:

## Measured numbers

Against a base of 2,000,000 billings and 5,000 customers.

| | |
|---|---|
| Full dashboard | **0.66 – 0.93 s** |
| Report, one month for one customer | **0.24 s** |
| Report, a one-year scope | **12.9 s** uncached, **~3 s** cached |
| The totals aggregation | 8.2 – 8.5 s |
| Reading one billing's trail | 0.127 ms |
| PDF cap | **1,000 rows** — 420 MB for a thousand, over 3 GB for five thousand |
| Cost of one commit in this environment | 183 – 360 ms |
| Loading the 2,000,000 records | **46 – 49 min** with the indexes deferred — 310 with them present |

Three of these measurements **changed decisions that had already been made**: the
PDF cap dropped from 5,000 to 1,000, the one-year scope did not take 6 seconds
but 12, and the first idea for cache invalidation had a race and was discarded
before it became code. All three are recounted in
[docs/performance.md](docs/performance.md).

## Use of AI

Development was carried out with **Claude Code**, and the files that steer the
agent are under version control — `CLAUDE.md` and `.claude/skills/`, as the brief
asks for. What is worth recording is not the tool, it is where the configuration
changed the outcome: a test before the code on every business rule, frozen time
in the interest tests, and **two instructions that did not survive measurement**
and went back into `CLAUDE.md` corrected.

The full list, with the skills used and the effect of each one:
[docs/ai.md](docs/ai.md).

## What would be left for production

Materialised totals, partitioning by date, a FULLTEXT index on the description,
asynchronous exports and a read replica. Each item is in
[docs/production.md](docs/production.md) with the measurement that justifies it — a
pending item is only worth recording if it comes with a number.
